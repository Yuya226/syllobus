## 開発者による復旧手順

1. Supabase管理画面で対象プロジェクトの状態を確認。Pausedの場合だけ復旧操作を行う。
2. プロジェクトURLとサービス用キーが同一プロジェクトの有効なものか確認。`SUPABASE_SERVICE_ROLE_KEY` を公開環境変数にしない。
3. VercelのProduction / Previewを区別し、Supabase URL・サービスキー、Google認証3項目、Upstash URL/トークン、`PARSER_VERSION` を設定。Previewは専用DBを使う。
4. `WRITE_TOKEN_SECRET` に十分ランダムな32文字以上の秘密を設定（例: `openssl rand -hex 32`）。既定値は廃止。変更すると既存Cookieは無効になり、新セッションになる。過去データをIDだけで再取得する救済は設けない。
5. DBバックアップ・スキーマを確認し、既存マイグレーション001・002の適用状況を確認。新規DBは基礎テーブル定義がリポジトリにないため、このSQLだけでは構築できない。
6. `supabase/migrations/003_session_security.sql` をまず検証DBで適用。`session_id` がuuid、記載カラムと既存複合UNIQUEがあることを確認。本番適用はスキーマ一致と回帰試験を確認してから。
7. 新しいデプロイでビルド・APIを確認。統計RPCが存在しなければ001→002を確認して適用。500の詳細原因はVercelログで調べる（成績本文・秘密をログに追加しない）。
8. 検証DBで2つの独立ブラウザを使い、保存→復元→再保存→削除、他セッションの読取・書込・削除403、Cookieなし403、失敗時に元データが残ることを確認。
9. Supabase RESTへのanon/authenticatedによる成績テーブルとRPCアクセスが拒否されること、既存のビューやSECURITY DEFINER関数から漏れないことも確認。
10. 公開するデモURLは `/dashboard?demo=1`。API・DBが使えなくてもデモは動作する。

## プライバシーと制限

- 元画像はGoogle Cloud Visionへ送信。アプリは元ファイルを保存しない。CSVは端末で解析し、抽出した成績を補完APIへ送信。
- 確認済み成績はブラウザに保存。明示的同意を選んだ場合のみSupabaseに保存。保存項目はAPIとAboutに列記。
- 削除は同じブラウザの認証Cookieが必要。Cookie消失・旧シークレットの失効で所有権を証明できない旧データは、自動復元・削除不可。運営が個別対応の本人確認方針を決める必要がある。
- 「もう一度」は端末データのみを消す。サーバー削除は専用ボタン。
- IP制限が利用できない場合は解析・保存を503にし、無制限の有料OCR利用を防止。
- 10未満の集計は非公開。同一評語だけの科目分布も抑制。順位APIは任意GPA照会による分布復元を防ぐため停止。学部別平均は差分推測を避け停止。
- 標本はセッション単位であり人数を保証しない。任意投稿・重複端末・投稿の正確性に限界がある。閾値は完全な匿名性の保証ではない。時系列差分・複数投稿による攻撃対策（固定集計期間等）は将来課題。
- デモは実統計を表示しない。既存の実成績localStorageを変更しない。
